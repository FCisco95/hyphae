### C4. Apply 0010–0012 (Cisco)
- **Run:** the agent reruns C2's activity check first. Then, from `packages\db`, over Neon's **direct** endpoint with a 3-second lock timeout, the URL built from `.env` without pasting it:
  ```powershell
  $u = ((Get-Content ..\..\.env | Select-String '^DATABASE_URL=').Line -split '=', 2)[1].Trim()
  $env:DATABASE_URL = ($u -replace '-pooler\.', '.') + '&options=-c%20lock_timeout%3D3000'

  node node_modules\drizzle-kit\bin.cjs migrate
  Remove-Item Env:DATABASE_URL
  ```
  - **Why this URL:** `.env`'s `DATABASE_URL` is Neon's pooler, which refuses a lock timeout in the startup packet (`unsupported startup parameter in options`). The direct endpoint takes it only as `options=-c lock_timeout=…`; a bare `lock_timeout=` URL parameter is silently ignored there (read back as `0`). drizzle-kit connects through the `pg` driver here. All three read on Neon on 2026-09-30, read-only.
  - **Why 3 s:** 0010's `ALTER TABLE`s wait at most 3 s behind a `/submit` that holds a row lock, so later `/submit`s queue behind the migration for at most that long. Once it has its locks, the migration finishes in about a second on these tables.
- **Check:** `migrations applied successfully!`.
- **If it fails on the lock timeout** (`canceling statement due to lock timeout`; the migrator exits 1 and rolls back, so nothing is applied): the agent confirms the journal still reads 0000–0009 and lists what holds a lock on the four tables (`pg_locks` joined to `pg_stat_activity`). Wait 30 s, rerun C2's activity check, then run the same command again. **At most three attempts.** After a third timeout, stop: whether to pause reward intake for the migration (`scripts/reward-intake.ts <MYCEL mint> pause`, then `resume` after C5) is Cisco's decision.
- **If it fails for any other reason:** stop. Nothing is applied; fix the cause, then run it again.
- **Rehearsed** on Postgres 17 in Docker (2026-09-30) with this migrator and these files: with 0000–0009 applied and a `/submit`-style `ROW EXCLUSIVE` lock held on `reward_intakes` (and, in a second run, on `reward_decisions`), the command exited 1 after 4.3–4.5 s with the journal still at 10 rows, no 0010 column and no 0011 table; with the lock released, it applied 0010–0012 in 1.0 s and the journal read 13.

### C12. Deploy, signed by the Ledger (agent runs; Cisco approves)
- **Run** on Windows, with the hot key as fee payer:
  ```powershell
  solana.exe program deploy --buffer <BUFFER> --program-id target\deploy\hyphae-keypair.json `
    --upgrade-authority "usb://ledger?key=2/0" --keypair <hot key file> -u <rpc> `
    --with-compute-unit-price <µlamports> --output json
  ```
  One transaction: create the program account, then `DeployWithMaxDataLen` (max length 229,432; later upgrades extend it automatically). Its signers are the hot key, the program keypair and the Ledger.
- **Check:** the command prints the signature.
- **Ledger approvals:** **1** (blind), for `2kz1Zq…` as upgrade authority.
- **If it fails:**
  - **Rejected on the device, or the device timed out before signing:** nothing was signed, so nothing can land. The buffer stays with the Ledger for a retry.
  - **Anything after the device signed** (a CLI error, an RPC timeout, a lost confirmation): a signed copy may still land, and the CLI may have re-signed with fresh blockhashes.
    - **Why a retry is still safe:** every copy, and any retry, creates the same program address from the same buffer, which holds the verified bytes under `2kz1Zq…` and which no hot key can change (C11). The first copy to land creates the program and consumes the buffer. After that, any other copy fails: the program account already exists and the buffer is gone. The buffer's key was deleted in C11, so the address cannot be recreated with other bytes, and a retry that finds the program already there has no buffer to upgrade from. So at most one deploy lands, and it is always the verified build under the Ledger. A premature retry costs a failed transaction and one more device prompt, never a second or different program.
    - **Recovery:**
    1. Wait for the signed copies to lapse, so a retry is not wasted: record `H = solana block-height -u <rpc> --commitment processed` as the CLI exits, then wait until `solana block-height -u <rpc> --commitment finalized` is above `H + 300`. This is not a proof: a lagging RPC node can report a low `H`. The safety comes from the reason above.
    2. Read, each with `-u <rpc> --commitment finalized`:
       - `solana transaction-history 2kz1Zq8UDm9Hq6XwPW6cViQZe7aySEBGk1gLWN8gofjR`: the Ledger signed every copy, so any landed deploy is listed;
       - `solana program show EAz8WkyU…d6E`;
       - `solana program show <BUFFER>`.
    3. A deploy in that history, or the program present: it landed. Continue with C13's readback.
    4. No deploy, no program, and the buffer still under `2kz1Zq…` with hash `7e902d1b…43ac`: retry C12. If the retry itself fails because the program now exists or the buffer is gone, a late copy landed: go to C13's readback.
    5. Anything else, or any doubt: stop and ask Cisco.
- **Rollback:** **no rollback** for a landed deploy. The Ledger alone can upgrade the program (a new reviewed build, same sequence) or close it.
