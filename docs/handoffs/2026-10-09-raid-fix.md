## What changed, per finding

### 1. Medium: a cancellation could land between the claim and the send

Before, the claim committed `status = sending` and released the task lock; `/cancel_raid` could then finish, and the recap was still posted.

Now `deliverRaidRecap` runs in its own transaction:

1. `SELECT … FROM tasks WHERE id = $task FOR SHARE` (waits for a close or cancel in flight).
2. Reads the task's `cancelled` lifecycle event. If there is one: `status = skipped`, `reason = raid_cancelled`, nothing is sent.
3. Otherwise it sends while still holding the lock, then records the outcome and commits.

So a cancellation that committed first stops the recap, and one that comes later waits until the bounded send (4 s `AbortSignal.timeout`, unchanged in `runner.ts`) has finished. The committed at-most-once claim is unchanged. The community reward lock is never taken in this transaction (`dbClock` is a plain SELECT). Lock order stays task first; `transitionRaid` still takes task NO KEY UPDATE, then community.

### 2. Medium: a stale claim could skip a 429 deadline

Before, the claim's `ON CONFLICT DO UPDATE … WHERE` only checked `status = 'pending'`. A process that selected the raid before another process recorded a 429 deadline could flip the row back to `sending` and send early.

Now the conflict update requires both, checked on the conflicting row itself:

```sql
WHERE "raid_recaps"."status" = 'pending' AND "raid_recaps"."next_attempt_at" <= <due>
```

If that fails, RETURNING is empty and the caller gets no claim. The candidate SELECT is unchanged.

### 3. Low: no bound on 429 retries

Decision taken by the architect: one retry. The claim that re-takes a `pending` row (only a 429 leaves a row pending) sets `retry_used = true` in the same conflict update and returns it. A 429 on that retry records `status = failed`, `reason = rate_limit_retry_exhausted`. Missing or invalid `retry_after` still means 60 s. A retry whose deadline falls after the one-hour window stays `pending` and is never sent. Network errors and 5xx stay `uncertain`, never retried; 400/403 stay `failed`.

No member-visible text changed. The two new reasons (`raid_cancelled`, `rate_limit_retry_exhausted`) live only in `raid_recaps.reason`.

`apps/api/src/raid-alerts/recap.pg.test.ts` (real Postgres, separate pools):

| Test | Before the fix |
|---|---|
| a cancellation that commits before the send stops the recap | fails: `sent` |
| a cancellation waits for an in-flight recap send to finish | fails: the cancellation confirmed while the send was open |
| a claimer paused before its insert cannot take a recap another process deferred | fails: the paused claimer got the claim (the finding reproduced) |

The last test pauses a real `claimRaidRecap` between its candidate SELECT and its INSERT. It uses a third pool whose `raid_recaps` INSERT waits for a test gate (a Proxy over the postgres-js client's `begin`/`unsafe`). No lock can create that pause, because the other claimer runs the same statements. While B is paused, A claims, gets a 429 with `retry_after: 30` and records the deadline. Then B resumes and gets no claim. A claim 1 ms before the deadline gets nothing. At the deadline, two racing claimers yield exactly one, and it sends with `retry_used = true`. The gate relies on drizzle-orm 0.45's postgres-js session calling `client.unsafe(query, params).values()`. If a drizzle upgrade changes that, this test fails loudly; it does not pass silently.

## Open questions and limits

- While a recap send is open (at most the 4 s bound plus database time), `/cancel_raid` and `/close_raid` on that raid wait for it. Alert delivery already does the same. Intake's FK KEY SHARE and other SHARE readers are not blocked.
- A recap already posted stays visible if the raid is cancelled afterwards. That is the existing cancel rule; this fix only stops a send that has not started.
- A crash between the claim and the send still loses that recap in `sending`. That is the at-most-once side, as before.
- Release still needs: the independent Codex fix review, the 0018 + 0019 rollout pin with the hash above, and Cisco's yes on the recap texts in `2026-10-08-raid-stats.md` (unchanged).
