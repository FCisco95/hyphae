## Review of the PR diff (`aebb147...bcdb328`)

### Lock then clock (`config.ts:175-191`)

`withCommunityLock` opens one transaction, takes `SELECT … FROM communities WHERE id = $1 FOR UPDATE`, and only then reads `clock_timestamp()` through `dbClock` (`config.ts:162-171`). Under READ COMMITTED (Neon's default) the `FOR UPDATE` waits for any earlier writer to commit and returns the latest committed row, so a second writer's `now` is strictly after the first writer's commit. The lock is held to commit. `acceptedAt` is therefore monotone per community and equals commit order (I-3). The ms extraction `floor(extract(epoch from clock_timestamp()) * 1000)::double precision` is exact for a 13-digit integer. Verified by reading; PGlite is single-connection so no test can exercise two writers.

### Materialization loop (`config.ts:267-311`)

- Loop condition `last.closesAt <= t` with `nextWindow` giving `opensAt = previous.closesAt` yields the half-open window (I-1) and contiguity (I-2). After any iteration `last.opensAt <= t` holds, so the trailing "containing epoch" query only runs when no epoch was created and `t` precedes the latest epoch, which for `t = now` means "before epoch 1" and returns null.
- Each iteration re-reads the pending proposal, so a proposal activated at index `n` is no longer pending at `n+1`; the duration for the new window comes from the config pinned to the new epoch, not the previous one.
- Nothing opens after `t` (I-6), so a pending proposal always targets an unmaterialized epoch.
- A legacy epoch without a pin throws once it has closed (`config.ts:277-279`); see observation 3.

### Admission guard order (`intake.ts:44-122`)

idempotency → pause → epoch (`not_open`) → legacy pin → member (new) → task open → artifact duplicate → insert contribution → insert intake. Returning the existing intake on redelivery even while paused (deviation 1 in the implementation record) is the right call for an at-least-once webhook. The `contributions` insert uses the lock clock for `submittedAt`; the intake copies `epoch.rewardConfigId`. Unique indexes back the two lookups (`0003_reward_config_intake.sql:54-55`).

### Cooldown arithmetic

`earliestActivationEpoch(k, a) = max(k + 1, a + 2)` (`config.ts:120-121`). `proposeRewardConfig` materializes up to `now` first, so `k` is the epoch that contains the acceptance instant and `a` already includes any activation that materialization just performed (`config.ts:395-406`). Before epoch 1 opens, `k = 0` and bootstrap counts as `a = 1`, giving E3. The PGlite scenario in `intake.test.ts:354-449` reproduces the proposal's worked table (E10→11, E11→13, E12→13 superseding, boundary acceptance at `closesAt(E12)` → E15, 120 s E13 with no gap or overlap).

### Migration `0003_reward_config_intake.sql`

Matches `packages/db/src/schema.ts`: one enum, three tables, two nullable columns, nine foreign keys, the partial unique index on pending proposals, the three unique indexes on intakes. All additive; no `NOT NULL` on existing tables, no backfill, no `CONCURRENTLY` needed because every indexed table is new or empty on Neon. `pnpm exec drizzle-kit check` → "Everything's fine"; `pnpm exec drizzle-kit generate` → "No schema changes, nothing to migrate", so snapshot 0003 and the schema agree. Applying it stays a separate authorized step.

### `Db` type and test database

`Db = PgDatabase<PgQueryResultHKT, typeof schema>` lets PGlite and postgres-js share the functions; typecheck confirms the transaction handle is assignable. `test-db.ts` lives under `src` but tsup entries are `server.ts` and `worker.ts` only, and `@electric-sql/pglite` is a dev dependency, so nothing ships to Fly.

## Non-blocking observations (for R3/R5 scope, not for this PR)

1. **Lock mode** (`config.ts:186`). `FOR UPDATE` conflicts with the `FOR KEY SHARE` that every FK insert into `members`, `tasks` and `contributions` takes on the community row, so the legacy bot's `/link`, `/raid` and `/submit` inserts queue behind reward writes and vice versa. Short transactions, no deadlock cycle, but `for("no key update")` gives the same mutual exclusion among reward writers without blocking FK inserts. Decide when R3 rewires `/submit`.
2. **`ensureEpochAt(tx, id, t, now)`** (`config.ts:267-271`). Every caller passes `t === now`. Keep if R5's close needs `t` at the boundary and `now` for `resolvedAt`; otherwise collapse.
3. **Closed legacy epoch** (`config.ts:277-279`). A community whose last epoch has no pin and has closed makes admission throw instead of returning `legacy_epoch`, and bootstrap refuses any community with epochs, so there is no path from legacy to pinned. Neon's `epochs` is empty today. The cutover checklist should assert zero epochs for MYCEL before bootstrap.
4. **Re-proposing the pending config** (`config.ts:400-414`). Proposing the same payload that is already pending supersedes it with a new row whose earliest epoch may be later. Harmless; could be treated as a no-op like the pinned case.
5. **Staging update before the reward write** (`scripts/set-rubric.ts:45-49`). A failing bootstrap (for example `opensAt` not in the future) leaves the staging rubric changed, the same shape as documented deviation 4. Reordering to run the reward write first would make the script atomic in practice.
6. **`resolvedAt` on activation** (`config.ts:296`) is the materialization instant, not the epoch boundary; the boundary is the epoch's `opensAt`. Fine as audit data, worth a comment.
