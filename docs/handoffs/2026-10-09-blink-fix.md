# Claim Blink fix, 2026-10-09

Built by Claude Sonnet 5.5 as an Orca worker, branch `FCisco95/blink-fix` from `origin/next` (300eb97). Fixes the findings in [the Codex review](../reviews/2026-10-08-blink.md). Web only (`apps/web`): `lib/actions.ts` and the Action route. `lib/claim.ts`, the claim page, the API, packages and migrations are untouched. The `actions.json` route needed no change. Code commit `138c4d0`. Nothing pushed, merged or deployed.

## What works

1. **Body limit (medium).** `POST` reads the body through a byte reader and counts UTF-8 bytes as chunks arrive. Past 1024 bytes it cancels the stream and answers `413`. A stream that fails mid-read answers `400` through the same safe path (JSON, CORS, `no-store`), never a rejected promise. The content type is now explicit: `application/json`, with an optional `charset=utf-8`; anything else, or none, answers `415`. Every rejection reads nothing from the API.
2. **Claim transaction on "already claimed" (low).** The `409` for a paid leaf now ends with the explorer link for that claim transaction, on the leaf's network (`?cluster=devnet` only on devnet), from the same `explorerTx` helper the claim page uses. A `paid` payment with no `claim_tx` is still refused (503; the read schema rejects it).
3. **Chain on errors (low).** Once the epoch read has shown a published allocation, or the claim read has returned a leaf, failures carry `X-Blockchain-Ids` for that network: no leaf (404, from the epoch's network), paid (409), unavailable payment (503), builder refusal (503) (from the leaf's network). No chain is invented where none is known: malformed link, epoch read failed, epoch not published, bad body.

The transaction bytes are unchanged; the existing byte-equality test with `claimTransaction` passes untouched.

## New member-visible strings (for Cisco's approval)

| Case | Status | Text |
|---|---|---|
| Body over 1 KiB | 413 | `That request is too large.` |
| Not JSON | 415 | `Send the request as JSON.` |
| Body cut off mid-read | 400 | `That request could not be read. Try again.` |
| Already claimed | 409 | `This wallet already claimed epoch 2. Transaction: https://explorer.solana.com/tx/<signature>` (devnet adds `?cluster=devnet`) |

The 400 string is a fourth one the brief did not name; it was needed for the stream-failure path, which the review wanted distinct from the invalid-wallet message.

## Open questions

- Is the 400 "could not be read" string fine, or should a failed read share the 413 text?
- A blink client that omits `Content-Type` on the POST would now get 415. The Actions spec has clients send JSON, but this was not checked against a live client. Re-check at the registry step.
- The charset rule rejects anything but UTF-8. Say if a looser rule is wanted.
