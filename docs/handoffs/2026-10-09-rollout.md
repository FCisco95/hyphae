## What the script now checks

The release plan it serves is `docs/demo/2026-10-11-release-plan.md`. The architect is writing it; it does not exist on this branch yet.

- **Pinned migrations.** `0018_member_wallet_links_wallet` and then `0019_raid_recaps`, pinned by the SHA-256 of their SQL files. The pin check now runs in **every** mode, not only `migrate`. A migrations folder that does not end with exactly these two files, in this order, at these hashes, stops precheck, migrate and postcheck with `ERROR the migrations folder does not end with this release's pinned migrations: it ends with <tag> sha256 <hash>, ...`.

  | Migration | SQL SHA-256 |
  |---|---|
  | `0018_member_wallet_links_wallet` | `79592f957d9b43805e468c97ffce066a091a68cfaebda5944f9d234282812302` |
  | `0019_raid_recaps` | `6d3f708b25b1fa32218bcd18266723661f9d34f22ebe4252e19702a5a6fe592c` |

- **Shape that holds before and after.**
  - 0015: the three `members` columns are nullable and `members_wallet_link_together` exists.
  - 0017 (no longer a swap): `reward_config_amendments` has exactly its three checks and exactly one unique index, `reward_config_amendments_epoch_from(epoch_id,from_config_id)`.
  - Enum `public.raid_delivery_status` exists with labels `pending, sending, sent, skipped, failed, uncertain`. 0019 reuses this enum.
- **Before the migration (pre shape).** There is no relation `public.member_wallet_links_wallet` and no `public.raid_recaps`.
- **After the migration (post shape), read from the catalog.**
  - `member_wallet_links_wallet` is a btree index on `member_wallet_links(wallet)`. It is a single column, not unique, not partial, and valid.
  - `raid_recaps` has exactly 0019's eight columns, in order, with their types and nullability. It has no defaults.
  - Its constraints are exactly `raid_recaps_pkey p (task_id)`, plus two foreign keys: `task_id -> public.tasks(id)` and `community_id -> public.communities(id)`, both `NO ACTION`. Its only index is `raid_recaps_pkey`.
  - Types and referenced tables are schema-qualified, so the result does not depend on `search_path`. Constraints of kind `n` are excluded, so Postgres 18's not-null constraints do not break the comparison.
- **Epoch state at release time.** Hyphae Lab has exactly 3 epochs:
  - Epoch 1 is `closed` with 1 snapshot.
  - Epoch 2 is `closed` **or** `published`, with 1 snapshot and `closes_at = 2026-10-10T00:00:00Z`. Its `status = published` must agree with a non-null `publish_tx`, because `publish.ts` writes the two together.
  - Epoch 3 is `open`, `2026-10-10T00:00:00Z` to `2026-10-17T00:00:00Z`, with 0 snapshots.
  - Unchanged checks: `first_paid_epoch = 2`, intake not paused, one community, the Hyphae Lab mint and name.
- **Public reads.** The script reads `/v1/communities/<mint>`, `/epochs/2` and now `/epochs/3`.
  - Every public epoch must match the database on window and status. Both `closed` and `published` in the database read as public `closed`, because the API derives `closed` from the snapshot.
  - Epoch 2 must be `closed: true` on the same reward config. Epoch 3 must be `status: open` on the same reward config.
  - Epoch 2's publication is **recorded, not required**. The report has a new `epoch2_publication` field: `{database, public, public_reason}`.
  - Only one publication case fails: the API shows `published` with a `publish_tx` the database does not hold.
- **Counts.** `raid_recaps` is in `COUNTED_TABLES`.
  - Before 0019 the table does not exist, so its count is 0. The shape says whether it exists.
  - In every phase, a `raid_recaps` row fails the check with `raid_recaps has N row(s): only the new image writes recaps`.
  - The baseline rules are unchanged: counts may only grow, `reward_config_amendments` must not change between the precheck and the postcheck, and liveness still needs a newer `reward-recovery` completion.
- **Unchanged:** read-only prechecks, `lock_timeout=3s` as a startup option, the direct (non-pooler) host, the URL-parameter allowlist, the channel-bound login, liveness, and exit codes 0/1/2. Nothing from `DATABASE_URL` is printed. The lock-timeout message now says "Retry per the release plan (max 3)" instead of naming the old plan's Step 5.

### Two bugs the rehearsal found (fixed before the recorded run)

The first two runs failed in the new `raid_recaps` constraint read. The release guard did what it should both times: the migrate committed, the read-back failed, and the script printed `STOP: migrator returned but the journal or the schema is not as expected` and exited 1. It did not claim success.

1. `ERROR 42725 operator is not unique: text || "char"`. `contype`, `confupdtype` and `confdeltype` are of type `"char"`. Fix: cast them with `::text`.
2. `ERROR 42703 column k.conrelid does not exist`. The `columnList` subquery's alias `k` shadowed the outer `pg_constraint k`. Fix: the subquery's aliases are now `col_key` and `col_att`.

After each fix, the database was rebuilt from the untouched clone (`release_base`). The run below is the first clean pass, from a fresh 18-row journal.

## Open questions

1. **Epoch 2 publication is not required.** The precheck passes when the API shows epoch 2's allocation as `unavailable` even though the database has a `publish_tx`, because a failed chain read looks the same. The operator should read `epoch2_publication` in `pre.json`. Should the 2026-10-11 plan require `public: "published"` before migrating? Recommendation: yes, as a step in the plan, not in the script. The release runs after the payout, so anything else means something to investigate first.
2. **Epoch 3's close is pinned to 2026-10-17T00:00Z.** This assumes the config pinned at the close keeps the 7-day duration. `ensureEpochAt` uses the activated pending config, or epoch 2's config, for the duration. If a config with another duration activates at the close, the precheck fails. That is intended, but the plan should confirm it.
3. **Order against epoch 3's amendment.** The baseline comparison fails if any amendment is recorded between precheck and postcheck. The plan must record epoch 3's `reward-eval/3` amendment after the postcheck, once the new image runs.
4. **Locks.** drizzle runs both migrations in one transaction under `lock_timeout 3s`.
   - 0018's `CREATE INDEX` is not concurrent. It takes SHARE on `member_wallet_links`, which blocks writes to that table for the duration of the build. The table is small.
   - 0019's two foreign keys take SHARE ROW EXCLUSIVE on `tasks` and `communities` briefly.
   - Under contention the result is a clean exit 2.
5. **Rehearsal stand-ins.** The rehearsal `pgboss.job` holds only the columns `db.mjs` reads; it is not pg-boss's full schema. The rehearsal server is Postgres 17.11. Neon's version is recorded in `pre.json` `state.server.version`.
