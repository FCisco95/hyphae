## Step 6: the `test:pg` race, cause and fix

Measured with temporary per-round timing (not committed), on a fresh Postgres 17 each run:

| Load | P2 test | Per round |
|---|---|---|
| Idle | 23.4 s | setup 60 ms, race 364 ms (p50): mostly the test's own 0–600 ms delay and 300 ms boundary |
| 16 CPU hogs in the WSL/Docker VM | 28.7 s | setup 108 ms (p50) |
| 32 hogs plus the full unit suite in parallel (load average 34 on 16 cores) | **timed out at 60,019 ms after 26 rounds** | setup 1.0–3.2 s, race ~0.8 s |
| Same load, whole file, timeout lifted for measurement only | passed | the first 50-round test took **101 s** (4.8 s idle) |

- **Cause:** each round is real Postgres work, and host saturation slows it 20–50×. Every 50-round loop shares the file's 60 s default. P2 flaked first because it has the least headroom. Every finished round's assertions held.
- **Ruled out:**
  - clock skew: the boundary and the lock's clock are both Postgres `clock_timestamp()`;
  - a hang: every non-closing path throws, and per-round logs show steady progress;
  - close starvation: polls complete.
- **Fix** (`59ebcab`): the three round-loop suites get 4 s a round (200 s); the lock-mode test keeps 60 s. A 1 s probe confirmed Vitest honours the suite option. Under the same load the whole file then passed: nomination 119.7 s, P2 29.7 s.
- **Also seen under that load:** the unit test `eval-scoring.test.ts` (a child-process dry run) exceeded its 5 s default once. It passes in every normal gate; not touched.
