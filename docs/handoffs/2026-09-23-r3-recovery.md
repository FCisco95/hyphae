## F3 decision (needs Cisco)

A crash after `completeDispatch` commits and before `reward-notify` is queued loses the member's score message. The work is recorded correctly; only the Telegram reply is lost. Two ways to close it:

1. **Recommended: migration 0005, additive.** A nullable `reward_decisions.notified_at timestamptz`. `notifyReward` sets it after Telegram accepts the message; the sweep adds part (c), re-queueing completed decisions with `notified_at` null past the grace. At-least-once: a crash between Telegram's accept and the marker write can send the message twice. Applied together with 0003/0004 there are zero rows to backfill. R5's planned migration becomes 0006.
2. **No migration: transactional enqueue.** Insert the `reward-notify` job inside `completeDispatch`'s transaction through pg-boss's per-call `db` option (pg-boss documents this). Exactly-once queueing, but the reward module gains a queue hook, the Drizzle transaction needs a raw `executeSql` adapter, and PGlite tests need a fake sink. More code on the money path.

The approval covers only 0003/0004, so neither is started. Until one is chosen, F3 is a known, disclosed gap: a lost message, never a lost or duplicated score.
