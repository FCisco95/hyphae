# Can a Telegram participant sign Hyphae's `/link`?

Code-path assessment at `3a361e76801a78f0392ec0ca42dfb8ff1f1445d6`, October 3, 2026. **The signature is made by the participant's wallet in the browser that opens the private link. Telegram and Hyphae's server cannot produce it.** No Hyphae phone test was run here. Verdicts below distinguish a code requirement from a measured device result.

| Platform/surface | Verdict | Exact reason and next surface |
|---|---|---|
| Telegram for Android's internal browser, with no registered wallet | **FAIL (code path); device confirmation pending** | No wallet button and no signature call. Sentinel measured this absence in its Android Mini App; Hyphae opens an ordinary URL, so the exact Hyphae webview still needs testing. Copy the original private bot URL into a wallet's in-app browser. |
| Telegram Desktop internal browser, with no registered wallet | **FAIL (code path); device confirmation pending** | Same requirement. Sentinel's Desktop Mini App lacked providers. If Desktop opens an external browser instead, that browser decides the outcome: a compatible wallet extension can sign. Desktop's actual URL-opening preference is **UNKNOWN** here. |
| Mobile system browser (Chrome/Safari) | **UNKNOWN on a real phone; FAIL if no Wallet Standard wallet registers** | No native-app bridge, WalletConnect, Mobile Wallet Adapter or injected-provider fallback exists in this page. Having a wallet app installed is insufficient. A browser registering both required features could work; this was not measured. |
| Wallet's own mobile in-app browser | **UNKNOWN end-to-end** | It is the intended existing fallback; **PASS by code contract** only if it registers `standard:connect` + `solana:signMessage`, returns unchanged message bytes, and server verification commits. Phantom/Solflare and iOS need attended testing. |

**Sentinel's finding applies partially:** the missing-wallet failure applies unchanged to Hyphae's Wallet Standard discovery, but Sentinel measured a Mini App, whereas Hyphae issues a normal private browser URL. Hyphae already has a portable bearer link and needs no Telegram `initData` in the signing browser. Do not import Sentinel's cookie/redemption/confirmation design as if Hyphae already had it. iOS remains untested, not a measured failure.

## Exact trace

1. Group `/link` looks up the registered chat and sends `t.me/<bot>?start=link_<community UUID>`; private `/link` alone tells the user to start in the group ([bot registration](../../../apps/api/src/bot/index.ts), [command](../../../apps/api/src/bot/commands/link.ts)). Private `/start` checks `getChatMember`, then creates a 15-minute single-use session; only its token digest is stored ([session](../../../apps/api/src/link/session.ts)). The private message gives `LINK_ORIGIN/link#<token>`.
2. The API serves the signing page, separately from Vercel `/claim` ([mount](../../../apps/api/src/server.ts), [routes](../../../apps/api/src/link/routes.ts)). The [client, lines 4–5](../../../apps/api/src/link/page/client.ts) reads the fragment and immediately strips it from history. Its `render()` has only wallet buttons or “No Solana wallet found…”. **There is no copy/handoff control. Copying the address bar after load loses the token; return to the original private bot message.**
3. [Wallet discovery, lines 24–27](../../../apps/api/src/link/page/wallet.ts) accepts only Wallet Standard wallets with connect and message-signing features. After user selection, connect returns the first account; `/link/request` writes a proof request and supplies the readable message. `sign()` calls that wallet's `solana:signMessage` with exact UTF-8 bytes; the wallet surface asks the user and its key signs. The client rejects altered bytes, then posts the signature to `/link/verify`.
4. `@organichub/verify` **0.1.0** verifies signature, nonce, domain, chain and five-minute proof expiry; [store](../../../apps/api/src/link/store.ts) atomically consumes proof/session and writes [wallet history](../../../apps/api/src/link/wallet-links.ts). [Flow](../../../apps/api/src/link/page/flow.ts) reads `/status` on uncertain verification outcome instead of resending. The SDK message is generic Hyphae verification, **does not display the Telegram account**, and moves no funds; identity binding comes from the server session. No transaction is signed.

Record phone OS, Telegram/wallet/browser versions and the opening surface. This test creates link/proof/member records when run; the owner must authorize/attend it. No `/raid`, `/submit`, funding or paid model call is needed.
- **2–5 min:** tester sends `/link` in the registered group, follows their own private bot deep link, opens the private URL in Telegram. Record wallet buttons versus no-wallet text. Do not screenshot the raw URL/token. An absent wallet is a failure for **that surface**, not proof the whole flow is unusable.
- **5–8 min:** copy the **original bot message URL**, including its fragment, privately into the phone's system browser. Record discovery. If the token is missing/expired, get a new group `/link`; never copy the stripped address bar or another person's link.
- **8–12 min:** obtain a fresh link and paste it into Phantom's or Solflare's own browser. Select the wallet only if shown. Check exact API domain, wallet address and readable non-transaction message; cancel any transfer/approval/seed request. Sign, record success/error and shortened address, then return to `/me` in the group to confirm the same wallet is verified. Do not paste token/message/signature into a public receipt.
- **12–15 min:** record PASS only for a committed signed link matching `/me`; otherwise FAIL with surface/error, or UNKNOWN if not attempted. On uncertain success, check `/me` before restarting. Repeat a second wallet/iOS/Desktop as a separate sitting, with a fresh token. Recruitment stays parked until a real phone path passes.
