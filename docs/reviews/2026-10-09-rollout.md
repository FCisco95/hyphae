## Findings

1. **Medium — Compare epoch-detail windows and status with the database.** `scripts/rollout/db.mjs:510` (through line 515).

   The window/status loop validates only `live.community.epochs`. The epoch 2 detail is checked for its index, `closed` flag and config ID; epoch 3 for its index, status and config ID. Neither detail response has its open/close timestamps compared, and epoch 2's detail status is ignored. An API instance serving stale or incorrect detail dates can therefore pass the release gate despite disagreeing with the database and community endpoint. These are member-visible dates and states the rehearsal note says are checked.

   **Reproduction:** retain the correct database and community fixture. Change only the epoch-detail fixtures: epoch 2 reports `status: open`, `opens_at: 2026-10-01T00:00:00Z`, `closes_at: 2026-10-09T00:00:00Z`; epoch 3 reports `opens_at: 2026-10-09T00:00:00Z`, `closes_at: 2026-10-16T00:00:00Z`. Leave config IDs and epoch 2's `closed: true` intact. On **both PostgreSQL 17.11 and 18.6**, precheck returned `PASS`, migrate returned `APPLIED: journal 18 -> 20`, and postcheck returned `PASS`. Independent PG18 probes changing only epoch 2 status, only epoch 2 close, or only epoch 3 close also returned `PASS`. Controls with a wrong community-list close or epoch 3 detail status correctly failed.

   **Recommended fix:** validate each detail response's identity, window, public status and closed/final state against its database epoch and snapshot. Retain the intended mapping of database `published` to public `closed`; share the window/status comparison with the community-list checks.

   **Tests needed:** independent mismatches of each detail endpoint's open/close timestamp and status, plus inconsistent closed/final flags. Each must fail precheck/postcheck and refuse migrate without changing journal 18. Keep valid closed-unpublished and published epoch 2 fixtures passing.

2. **Low — Reject expression keys when asserting a single-column wallet index.** `scripts/rollout/db.mjs:286` (the `columnList` projection; helper at lines 340–343).

   `columnList` inner-joins each `indkey` item to `pg_attribute`. Expression keys have attribute number zero and disappear from the aggregate. The resulting `columns: wallet` does not prove a single-column index. This is a schema-drift detection gap, not a defect in pinned 0018 SQL or a demonstrated wallet-record failure.

   **Reproduction:** after a clean migration, replace the index on an isolated clone:

   ```sql
   DROP INDEX public.member_wallet_links_wallet;
   CREATE INDEX member_wallet_links_wallet
     ON public.member_wallet_links USING btree (wallet, lower(wallet));
   ```

   PostgreSQL reports `indnatts = 2`, `indnkeyatts = 2`, and a non-null expression tree. On **both 17.11 and 18.6**, postcheck returned `PASS`, reporting the expected object: `{table: member_wallet_links, method: btree, columns: wallet, unique: false, partial: false, valid: true}`.

   **Recommended fix:** require `indnatts = 1`, `indnkeyatts = 1` and `indexprs IS NULL`, alongside the existing checks. Missing attributes must not silently remove index keys. PostgreSQL documents expression entries and key/total counts in [pg_index](https://www.postgresql.org/docs/18/catalog-pg-index.html).

   **Tests needed:** wallet-only passes; wallet plus expression, expression-only, wallet plus another column, and included-column variants fail postcheck without changing schema or journal.
