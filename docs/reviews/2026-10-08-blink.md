## Verdict: CHANGES REQUESTED

**Findings: 0 high, 1 medium, 2 low.** Fix the body handling before release and cover the response gaps with regression tests. No transaction substitution, server signing, private signing key, or additional RPC client was found in the diff.

1. **Medium — Enforce the body limit while reading bytes.** `apps/web/app/api/actions/claim/[mint]/[index]/route.ts:25`, with `apps/web/lib/actions.ts:94`.

   The route calls `request.text()` before the size check, and the check counts UTF-16 string units instead of request bytes. An unauthenticated caller can make this handler buffer the entire permitted transport payload before rejection. A local probe streamed **81,920 bytes**: all 40 chunks were consumed, the stream was not cancelled, and only then did the handler return 400. A valid account plus 600 euro characters in an ignored field produced **666 string units / 1,866 UTF-8 bytes** and returned **200 with a transaction**, exceeding the documented 1 KiB cap. A failing body stream also rejects the route promise before its Action error/CORS wrapper runs. Hosting limits may constrain the impact; the handler itself does not enforce its advertised bound.

   **Recommended fix:** read with a bounded byte counter, reject oversized bodies with a 413 `ActionError`, and cancel the remaining stream. A `Content-Length` check alone is insufficient. Handle body-read failures through the same safe JSON, CORS and `no-store` response path. Distinguish an oversized or unreadable request from an invalid wallet instead of always telling the member to connect a wallet.

   **Tests needed:** just below/at/above the byte limit, multibyte JSON, a chunked body with no length header, an oversized stream that must stop early, and a stream read failure. Each rejection should perform zero API reads. The current oversized-string test passes after full buffering and cannot detect these failures.

2. **Low — Keep the transaction evidence when saying the wallet already claimed.** `apps/web/lib/actions.ts:130`.

   After a successful claim, clicking Claim again returns only `This wallet already claimed epoch 2.` The validated `payment.claim_tx` is discarded, leaving a member in the Blink without the transaction reference shown by `ClaimSummary` on the claim page. This loses the existing P14 presentation rule, paid with its transaction, recorded in the payment definitions and carried into the ruled R6 scope. The local paid-fixture probe returned 409 with no signature or evidence link in the body.

   This is a presentation defect, not fabricated payment: the read schema rejects `paid` without a valid claim signature, and the API verifies the receipt and its transaction. A separate probe with `claim_tx: null` correctly returned 503.

   **Recommended fix:** keep the 409 `ActionError` and include the verified claim transaction's network-aware explorer URL in its member-visible message. Use the existing explorer URL helper. Test both networks and preserve rejection of paid responses with missing evidence; the current paid test asserts only the evidence-free sentence.

3. **Low — Retain the known chain on POST error responses.** `apps/web/lib/actions.ts:42`, affecting the failures after the epoch or claim read at lines 119–142.

   `fail()` drops the network even when the validated epoch or claim has already identified it. The local devnet paid-fixture probe returned 409 with **no `X-Blockchain-Ids`**, while the corresponding successful response identified devnet. No-leaf, unavailable-payment and refused-builder responses have the same omission. Under the compatibility convention, absence denotes mainnet, so clients inspecting these responses receive inconsistent chain metadata precisely when displaying a failed devnet action. No wrong-chain transaction was observed; successful transaction responses carry the correct chain.

   **Recommended fix:** allow failures to carry the known network, using the published allocation's network before a claim exists and the claim's network after a successful read. Do not invent a network for requests where it is genuinely unknown. Add assertions for devnet and mainnet on the no-leaf, paid, unavailable-payment and builder-refusal responses; current error tests check messages but omit these chain assertions.
