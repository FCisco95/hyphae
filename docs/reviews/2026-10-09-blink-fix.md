1. **Low — Preserve the epoch's network when the claim read fails.** `apps/web/lib/actions.ts:163`.

   A valid JSON wallet request first reads a published devnet epoch, so `a.network` is already known. If the subsequent claim read returns HTTP 503, throws a transport error, or fails schema validation, the ternary returns the shared `UNREADABLE` reply without a network. The route returns 503 with no `X-Blockchain-Ids`, losing the known chain just as the earlier review described. Mainnet also omits its explicit header. No transaction is returned and no payment is fabricated.

   **Reproduced:** six in-memory web tests used `f.settledEpoch` / `onMainnet(claim).epoch`, then each of these claim outcomes on each network: HTTP 503; rejected fetch; `payment: { status: "paid", claim_tx: null }`. All six reached the expected 503 JSON error with CORS and `no-store`, performed exactly two API reads, and failed only the chain-header assertion: received `null` instead of the epoch's CAIP-2 ID.

   **Recommended fix:** return the same safe 503 message with `a.network` on this branch, for example a copy of `UNREADABLE` with `network: a.network`. Keep failures before a successful published-epoch read network-free. Do not infer a network from the rejected claim payload.

   **Tests needed:** add the six cases above to the route tests. Assert the epoch's devnet/mainnet header, 503, unchanged error JSON, CORS and `no-store`. Preserve the existing absent-header checks for malformed input and failed epoch reads. The existing "unreadable API" test fails the epoch read itself, so it cannot catch this branch; the new paid-without-signature test checks only status.
