1. **Medium — Keep the deadline active until the response body is consumed.** `apps/api/src/scoring/claude-client.ts:24` and `apps/api/src/scoring/claude-client.ts:30`.

   The transport relies only on the SDK's `timeout` option for its asserted 90-second upper bound. In the pinned `@anthropic-ai/sdk` 0.128.0, `client.mjs:663–675` starts the timer around `fetch` and clears it when `fetch` returns. The separate `internal/parse.mjs:29` subsequently awaits `response.json()` with no remaining deadline. Headers arriving promptly followed by a stalled or slowly delivered JSON body therefore keep `client.messages.create()` pending beyond 90 seconds. The existing timeout test holds `fetch` itself pending, so it does not cover this case.

   **Confirmed offline:** after explicit coordinator authorization, an inline Node probe imported the unchanged `claudeTransport`, supplied a fake key and mocked fetch, returned JSON headers immediately, and delayed the response body by 300 ms. With `timeoutMs: 40`, the call was still pending at **136 ms**, then **resolved successfully at 307 ms**. There was exactly **one request, no abort, and no body cancellation**. No network or probe file was used. The same timer is used for the production 90-second setting.

   This breaks the assumptions behind both the 180-second reward job expiry (`apps/api/src/jobs/queue.ts`) and the five-minute reconciliation horizon (`apps/api/src/jobs/reward-jobs.ts:56`). The provider call can still be reading a response when the job expires or another run classifies the dispatch as overdue; reconciliation is not reached at the promised timeout and the worker callback remains occupied. The dispatch fence still prevents an automatic second provider call; this finding does not claim a demonstrated duplicate charge.

   **Recommended fix:** create a per-call abort signal whose deadline remains armed across the entire awaited Messages call, pass it in the SDK request options, and dispose of its timer in `finally` after body parsing settles. Preserve `maxRetries: 0` and the exact request body. Do not use an uncancelled `Promise.race` that merely abandons an active read.

   **Tests needed:** extend `claude-client.test.ts` with a fetch that returns JSON headers immediately but whose body stalls, and one that delivers body chunks beyond a shortened deadline. Assert rejection and signal/body cancellation near that deadline, exactly one HTTP request, and successful completion for a body delivered in time. In `evaluation-claude.test.ts`, verify that this transport rejection parks the dispatch without a decision and that rerunning evaluation makes no second call.

## Limits and operational distinctions

- **A missing key before startup is not reconciliation.** `claudeDepsFromEnv` returns `undefined`; if the worker is otherwise able to boot, a new `/3` evaluation returns `not_ready/prompt_unavailable` without creating a dispatch. This is tested and preserves budget. With the default Anthropic `SCORING_MODEL`, the existing `defaultModel` initializer instead throws for an absent Anthropic key, before worker/bot startup. That boot dependency predates this branch; the new SDK does not remove it. An invalid/revoked key on an already configured transport throws during the call and reaches reconciliation. The brief's missing-key/reconciliation premise therefore needs this qualification.
- **Startup evidence is limited.** The tests load and exercise the installed SDK and both scorer modules. The production worker/bot was inspected, not booted against real external services. No new import-time network call or unconditional key requirement was found in the Claude module itself.
- **Release decisions remain separate.** The recorded H54 false pass and author-note questions about receipt wording, refusal policy, and the 65 baseline remain with the coordinator/founder.
